# Sensors and plan invariants

- Online is judged only by `isOnline` in `plan.ts`, on the service's clock at read time, and reaches the dashboard as the `online` field. A second copy of the 10 s rule (in the browser, or in another capability's module) reads a different clock and the plan and that capability disagree about the same sensor (see ADR-20261115051052164).
- A new sensor's default spot is chosen inside the one `INSERT ... SELECT` statement in `placeOnCheckin`. Splitting it into a read and then an insert lets two first check-ins arriving together land on the same spot.
- Every path that changes a sensor's placement by hand (move, nudge, facing, removal) runs `clearMeasuredMark` (`calibration/layout.ts`) in the same batch as its update. A path without it leaves "Calibrated" and the measured distances on a plan a researcher has since rearranged. Calibration's own `apply()` writes positions and facings directly, never through `placeSensor` (which would clear the mark it just set), and is the only writer that keeps the mark.
- A sensor's number is chosen inside the same `INSERT ... SELECT` in `placeOnCheckin` that places it, and only when it joins or returns. Splitting it into a read and a write lets two first check-ins take one number, and no unique index catches it: removed sensors keep their numbers to take back, so an index over the plan's numbers would make a rolled-back Worker (which returns a removed sensor with its old number as it is) fail that sensor's check-in.
- Names are worked out on every read, through `sensorNames` or a plan sensor's `name`, never stored on events or anything derived from them. A stored name would keep showing a removed sensor as the "Sensor N" another sensor now holds.
- Whether a sensor has the current sound list is judged only by `soundListState` in `plan.ts` and reaches the dashboard as the `sound_list` field, as online does; the sound list's reach count (`soundListReach`) uses the same meaning of "reported the current version". A second copy of the rule in the browser would disagree with the plan about the same sensor (agent-made).
- The behind count (`sensors.sound_list_behind`) moves only in the check-in handler (`noteSoundListCheckin`), never on an event delivery or in a check-in hook (hooks also run on a sensor's first contact through an event delivery). Moving it anywhere else turns "Outdated after 3 check-ins" into a count of requests, so a board posting events flips to Outdated without missing a check-in (agent-made).
