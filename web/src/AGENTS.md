# Worker invariants

- What keeps the researchers' data private is the session check on every `/dashboard/api/*` route, not the files: the dashboard's code under `/dashboard/` is public, because the public demo at `/dashboard/` runs it. Never put data, a secret or a researcher's recording in a file under `web/dashboard/`.
- The demo page (`demoPage` in `router.ts`) is the researchers' page rewritten to load `dashboard/demo/demo.js` before any other script; that module answers every `/dashboard/api/*` request in the browser. A dashboard module that reads data from any other path, or a script placed before that injection point, reaches the real service from the demo, where it is refused (or, once signed in on the same browser, shows the researchers' data in the demo). New data stays under `/dashboard/api/` and gets a simulated reply in `demo.js` (agent-made).
- `/` and `/signin` are in wrangler.jsonc's `assets.run_worker_first` with `/dashboard*` and `/api/*`: the researchers' page lives in the files at `/dashboard/`, so without the Worker in front `/` serves nothing, and without the session check in `router.ts` it would be served to anyone. The session cookie's path is `/` so that the page at `/` sees it.
- D1 refuses a query with more than 100 bound parameters. Pass a list of ids as one JSON parameter and expand it with `json_each` (as `api/events.ts` does), never one `?` per id: a 100-event batch plus the sensor id is 101.
- The served sound list is the enabled rows of `sounds` in `rowid` order, at the version in `sound_list`. Any change to a sound (switch, teach, delete) must also run `UPDATE sound_list SET version = version + 1` in the same batch, or sensors never fetch the change.
- Logs never carry the password, the sensor key or the cookie: `logLine` takes explicit fields, and request headers or bodies are never logged whole.
- Activities are grouped from the stored events on every read; directions and locations are computed once at arrival and stored on the event (see ADR-20261114163418117). Never add an activity table, and never recompute a line or point from the current plan on read.
- Clear events (`clearEvents` in `activities/activities.ts`) is one batch that deletes every per-event row. A capability that keeps per-event rows in a table of its own adds that table's DELETE to the batch, or a cleared rehearsal leaves its rows behind.
- Calibration runs and reports (`calibration_runs`, `calibration_participants`, `measured_layout`) are not per-event rows: Clear events never deletes them (see ADR-20261114171057932). A run advances only when a request touches it (a participant's check-in or report, a dashboard poll), through writes conditional on its status, so two requests advancing it at once apply it once; there is no timer to rely on.
- A pair's median rejects a bad round only with 3 or more rounds in each order, so the schedule runs 6 rounds (3 per order). With 4 (2 per order), one round far off makes the forward and reverse medians disagree and the pair fails as not repeatable, which real boards in a loud hall hit about one run in two (a noise lobe taken for a beep's first path); lowering `ROUNDS` (`calibration/calibration.ts`) loses that.
- A board with no audio reports `no_stream` 15 s after it learns of the run (`STREAM_TIMEOUT_S` in the library), at its next check-in (up to 3 s after the press by default, 1 s in the journeys). Before it is ready that report only makes it unready: `advance` leaves it out as soon as every other participant is ready (at least 2), or at `READY_WAIT_MS` (20 s after the press), and fails the run with `no_stream` only when too few others are ready. Treating it as fatal while waiting would let one deaf board fail a three-board run that could go ahead without it.
- A warning stores only its activity's newest event id at sending and belongs to whichever activity holds that event on read (`warnings/warnings.ts`, see ADR-20261114163418117). Its boards' outcomes advance by time on read (not picked up 15 s after sending, not confirmed 15 s after delivery), through the one `unsettled` rule that the card, the "on its way" refusal and the alarm on the check-in reply all use; a second copy of those windows lets the card say on its way while a Send goes through, or a board play after the card gave it up.
- Warnings read who is calibrating straight from `calibration_runs` and `calibration_participants` (status waiting or scheduled, not dropped). A change to what makes a run active or a participant left out in `calibration/calibration.ts` changes `calibratingSensors` with it, or a calibrating board gets an alarm mid-run.
